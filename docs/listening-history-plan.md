# 听歌记录：最近播放与个人排行

## 采用的方案

遵循侧边对话调研结论：侧栏仅新增一个「听歌记录」入口，页内切换「最近播放 / 最近一周排行 / 所有时间排行」。这是当前网易云账号的个人记录，与既有官方「排行榜」不同。

一起听已独立提交为 `d97ff94`，包含邀请二维码、结束轻提示以及后续独立心跳、曲终/拖动竞争和随机队列修复。新功能在 `features/listening-history` 分支开发。

第一阶段展示云端歌曲记录；第二阶段接入本机播放上报。不引入本地统计库或播客/视频历史。官方统计可能延迟，不把点击播放或接口成功等同于有效听歌次数。

## API 与数据

| 功能 | 接口 | 接入与语义 |
| --- | --- | --- |
| 最近播放 | `/api/play-record/song/list` | 直接复用 `RecentPlays(100)`；返回歌曲、毫秒播放时间与设备信息 |
| 个人排行 | `/api/v1/play/record` | `uid` 当前账号；`type=1` 最近一周，读取 `weekData`；`type=0` 所有时间，读取 `allData` |
| 播放上报 | `/api/feedback/weblog` | 独立 `clientlog.music.163.com` 域名，EAPI；`startplay` 与 `play` 两类事件，`time` 使用累计听歌秒数 |

最近播放保留 API 返回顺序、重复歌曲和跨设备记录，不经过 `pickup.go` 的 `lastStretch` 筛选。无已确认的 offset，不实现伪分页。排行保留服务端顺序，不按 `score` 重排，不将它当成次数；次数字段未经真实账号验证前不展示。排行兼容歌曲的 ar/al/dt 与 artists/album/duration 两种字段形态，权限补全复用已有 `detailPrivileges`。

源码依据：
- https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/blob/main/module/record_recent_song.js
- https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/blob/main/module/user_record.js
- https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/blob/main/module/scrobble.js

上游排行封装默认 WEAPI，本实现使用项目现有 EAPI 请求链路；未登录直连排行返回 `code=-2`，不能据此确认登录后的兼容性。尚未用真实登录账号调用新增排行接口，真机验收需要核对 EAPI、隐私限制与数据内容，不宣称完整互通已验证。

## 生命周期与交互

- 进入页面按需加载，渲染不无条件发请求；三个分页独立缓存，1 分钟内复用，手动刷新立即更新；同一分页最多一个在途请求，无后台持续轮询。
- 周期保存在路由中，前进/后退恢复周期及对应列表；切换时重置列表滚动，避免跨周期沿用位置。
- 回调检查账号 ID 与缓存对象身份；登出/重登替换整个记录状态，即使同账号重登也丢弃旧回调。
- 初次加载使用歌曲列表骨架；刷新失败保留原列表并提供重试；成功空结果替换旧列表且正常缓存。
- 未登录保留页面入口和登录按钮，不请求账号数据；空态仍保留分页与刷新。
- 最近记录展示当地时间，悬浮展示完整日期、相对时间和已知设备；时间缺失显示占位，不编造时间。排行沿用编号和时长，次数等待实测。

## 播放上报：协议与边界

调研依据为 API Enhanced 的 `module/scrobble.js` 及 `util/config.json`：使用独立日志域名、EAPI、`os=osx`，依次发送 `startplay` 和包含 `time` 的 `play`。上游对两类事件分别注释为最近播放与排行；这只是实现依据，服务端实际入榜规则仍需真机验证。

- 日志包含歌曲 ID、`type=song`、`mainsite=1`、`mainsiteWeb=1`；结束日志增加 `time`（整秒）、`end=playend`、`download=0`、`wifi=0`。沿用上游结束事件形式，不自行猜测其他结束原因枚举。
- 当前播放器不保留歌曲队列的来源歌单，不编造 `sourceId`、`source` 或 `content`。最小字段集是否被官方完整计入记录，需真实账号验收；若需要来源，再单独增加可追溯的队列元信息。
- 采样读取音频输出的实际播放位置，不读取拖动预览位置。仅累计正向进度增量，并以相邻采样的真实经过时间为上限；暂停、加载、缓冲停滞不累计等待时间。
- 所有输出 Seek 经过同一个包装，先采样后重置位置基准。手动拖动、一起听同步定位、恢复会话都不把跳过的位置计入听歌时长。反向拖动后的实际播放仍计入累计值，单次上报最多为歌曲总时长。
- 有正向音频进度才发送一次 `startplay`；自然结束、切换/清空歌曲、换账号和正常退出时发送一次 `play`。暂停/恢复不拆成多次播放，不在每次暂停时重复上报。累计不足一秒不发 `play`，不猜测 30 秒或播放比例等服务端门槛。
- 单曲循环或重新加载产生新的播放实例；同一实例的重复结束回调不会重复上报。一起听只统计本机实际音频，不按远端命令直接增加次数。播客排除在歌曲上报之外。
- 播放时每秒采样；暂停/空闲不持续调度。采样和状态更新在主线程，联网由独立串行 worker 执行，不阻塞播放或 UI。
- 队列上限 64 条，每次请求超时 8 秒。超时或失败不自动重试，因为请求可能已被服务端接收，接口没有已确认的幂等键。队列溢出时丢弃并提示；若开始事件未入队，不再发送该实例的结束事件。
- 上报器创建时捕获当前登录 Cookie，响应不写回全局 Cookie。换账号先结算旧实例，旧队列最多排空 3 秒，旧结果不能影响新账号 UI。正常退出异步等待最多 3 秒，再继续原退出流程。
- 上报成功只让听歌记录缓存过期，不触发后台连续刷新。失败在「听歌记录」页面保留轻量提示，不反复弹窗。

这是尽力同步：强制结束进程、长时间断网或退出时队列积压可能丢失记录；本期不增加持久化补报库。暂停后长期不切歌也不会立即发送结束日志。接口成功不保证最近播放/排行立即更新，真实门槛与延迟由网易云决定。

## 本地验证与验收

新增回归仅在 `.local/records/`，通过 Go overlay 注入并由本地 Git exclude 忽略，不提交。

已覆盖：
- 排行周期参数/对应分支、保持排序、两种歌曲形态、权限、业务失败及成功空结果。
- 最近记录的重复歌曲、跨设备和跨时间记录不被续播过滤。
- 导航、周期前进/后退、点击歌曲和播放全部使用当前列表；刷新去重、失败重试、空缓存、换账号及同账号重登的迟到响应。
- 未登录页面打开现有登录流程；常规和窄窗口、深浅主题的三分页渲染。

UI 和 API 回归连续 5 次通过，两个包的 race、MyGo vet 与 macOS ARM64 编译通过。完整测试仍仅有既有字幕相关 3 项与刘海播放器 2 项失败，日志位于 `/tmp/records-full-tests.log`。常规/窄窗、深浅主题的三分页渲染图位于 `/tmp/records-frames`。

真机重点：登录后核对最近记录和两个周期的排行，刷新与重试、账号切换、播放队列和右键操作。确认新增排行 EAPI 的真实响应后，再决定展示次数。


上报的本地回归覆盖实际进度累计、暂停不计时、拖动断点、外部控制曲终、重复结束去重、循环新实例、播客排除、队列溢出、超时不重试和有界收尾。协议测试解密请求，核对独立域名、秒数、账号 Cookie 快照及响应不污染后续登录。测试使用替身，不向真实账号发送模拟听歌记录。

真机上报验收：
1. 登录后完整听一首歌，再切换下一首；稍后在本客户端及官方端刷新最近播放和个人排行，核对歌曲。不要以一次接口成功直接认定排行计数生效。
2. 播放中暂停片刻、前后拖动，再继续听并切歌；确认播放交互正常，未把拖动跳过的部分算作实际时长。
3. 验证单曲循环、一起听切歌、关闭主窗口后台播放和正常退出；长断网后应保持播放可用，在听歌记录页显示同步不完整提示。
4. 如云端未更新，先用真实账号核对日志业务响应、最小字段集和云端延迟，再决定是否补来源信息；不要通过重复发送相同日志试探计次。

本次上报验证：player/app/netease 的本地回归及 race 连续 5 次通过，MyGo vet 通过；一起听旧测试修正等待心跳/命令回调的竞态后，目标回归连续 5 次通过。完整测试仍为既有 5 项失败，详见 `/tmp/scrobble-full-tests.log`。失败提示的三分页、常规/窄窗、深浅主题渲染位于 `/tmp/scrobble-frames`，已人工检查窄窗浅色布局。尚未验证真实账号上报后的云端统计结果。
