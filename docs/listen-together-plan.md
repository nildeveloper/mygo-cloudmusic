# 双人一起听：协议验证与代码实现方案

状态：首版代码已落地，已完成下述协议探测和本地回归；尚未完成集成客户端与官方端的完整实机互通验收。范围仅为双人一起听，不包含多人房间和“跟听”。

调研日期：2026-11-05。代码基线：`origin/main`，`fbc681f`（v0.1.27）。工作分支：`features/listen-together`。

## 1. 目标与范围

复用当前网易云登录与播放器，允许桌面客户端创建双人房间、邀请官方客户端加入，或加入官方客户端创建的房间，并同步歌曲、播放状态、进度及普通歌曲队列。

首版范围：

- 创建房间、解析并加入官方双人邀请、复制邀请链接。
- 显示对方头像/昵称、加入状态、连接状态及失败原因。
- 双向播放、暂停、上一首、下一首、点选歌曲、拖动进度和歌词跳转。
- 普通歌曲队列同步、进入时对齐、心跳、短暂断网后的状态恢复。
- 主窗口、媒体键、菜单栏、Touch Bar、刘海播放器操作经过同一个控制入口。
- 退出后恢复加入前的个人队列和播放位置，保持暂停。

首版不包含：多人/跟听、好友与私信系统、语音聊天、距离、表情、房间点赞、播客和私人 FM 协同、跨进程自动恢复房间。随机/循环协议通过验证后再纳入，不先假定可用。

界面入口放在现有播放界面，使用一个房间弹窗。无需增加永久设置项或另建设置模块；一起听是运行中的会话。

## 3. API 封装

下表为网易云上游路径，统一前缀 `/api/listen/together/`。Node 封装路由只是参考，本项目直接通过 Go 请求网易云。

| 后缀 | 主要请求字段 | 用途与验证重点 |
| --- | --- | --- |
| `room/create` | `refer=songplay_more` | 返回房间及创建者；检查是否返回已存在房间 |
| `room/check` | `roomId` | 可加入性，不代表已加入 |
| `play/invitation/accept` | `roomId, inviterId, refer=inbox_invite` | 加入后核对实际房间 ID |
| `status/get` | 无 | 当前账号是否在房、成员、房间信息 |
| `heartbeat` | `roomId, songId, playStatus, progress` | 上报当前实际播放快照，进度毫秒 |
| `play/command/report` | `roomId, commandInfo` | `commandInfo` 为 JSON 字符串 |
| `sync/list/command/report` | `roomId, playlistParam` | `playlistParam` 为 JSON 字符串 |
| `sync/playlist/get` | `roomId` | 读取队列及远端播放数据，结构以实测为准 |
| `end/v2` | `roomId` | 结束/退出的业务语义以 P7 为准 |

播放命令当前参考字段：`commandType, progress, playStatus, formerSongId, targetSongId, clientSeq`。维护真实的前一首歌曲 ID，不复制示例中固定的 `-1`。

队列命令当前参考字段：`commandType, version:[{userId,version}], anchorSongId, anchorPosition, displayList, randomList`。队列版本与播放命令序号分开维护。参考封装没有实际写出示例传入的 `playMode`，需单独验证；不认为复制示例就能同步随机和循环。

### 3.1 `internal/netease/listen_together.go`

采用绑定进入时登录凭据的 `ListenClient`，方法均接受 `context.Context`：

```go
Status(ctx) (ListenStatus, error)
Create(ctx) (ListenRoom, error)
Join(ctx, roomID, inviterID) error // check + accept，调用方继续核对 Status
Snapshot(ctx, roomID) (ListenSnapshot, error)
Heartbeat(ctx, roomID, songID, playing, progressMS) (ListenHeartbeat, error)
Play(ctx, roomID, command) error
Queue(ctx, roomID, userID, version, songIDs) error
End(ctx, roomID) error
Tracks(ctx, songIDs) ([]Track, error)
```

上面省略 Go 参数类型以突出职责。DTO 留在 `netease`，会话模块通过窄 API 接口调用；不建立重复的网络框架。

- `roomId` 用字符串；歌曲/用户 ID 使用 `int64` 或显式十进制转换，避免 `map[string]any` 将 ID 解成浮点数。
- `progress` 在边界转换为毫秒，内部使用 `time.Duration`。
- 命令对象和嵌套 JSON 使用 `json.Marshal` 编码，不拼接 JSON 字符串。
- 检查 HTTP 状态、顶层业务码和必要的内层成功字段；HTTP 200 不代表加入或指令成功。
- 缺失播放快照应返回“暂无快照”，不能以零值暂停、空队列覆盖本地。
- 接收端按绝对播放快照校验歌曲、非负进度和 PLAY/PAUSE 状态，不因官方新增 commandType 而拒绝完整快照；不将未知名称转换为本地操作。缺失或不完整的快照保留当前播放，稍后重读。

### 3.2 `internal/netease/eapi.go`

增加内部 `eapiRequest(ctx, path, data, out, cookies, saveCookies)`，原 `eapiPost` 作为兼容包装，所有现有调用点保持不变。请求使用 `http.NewRequestWithContext`，复用当前域名、设备 ID 和加密规则。

`ListenClient` 固定捕获进入房间时的 Cookie，一起听请求及退出清理均使用这份凭据，不读取后来切换的账号，也不把响应 Cookie 写回共享 Jar。取消与主线程回调身份检查一起阻止旧房间结果影响新会话。已验证的 EAPI 路径不引入 WEAPI 或运行时协议回退。

## 5. 播放器接入：集中接管命令

### 5.1 为什么不直接监听 `Changed`

`Player.Changed` 会在播放、暂停、seek、加载完成和歌词完成时触发，暂停淡出和 seek 还会异步重复发布状态。它适合刷新界面，不适合推导并上报用户操作。

保留 `Changed` 的现有职责；从明确的命令入口提交同步操作。这样歌词刷新、音源就绪和远端回放不会产生重复网络指令。

### 5.2 最小控制接口

在 `player` 中新增与房间无关的控制接口：

```go
// 在主线程调用。true 表示外部会话已接管，播放器不再执行默认动作。
Control func(Command) bool

// 目标为完整、确定的本地执行状态；不回调 Control。
func (p *Player) Apply(state Playback)

// 取消加载、seek、淡出和旧输出；支持恢复“加入前没有队列”的情况。
func (p *Player) Clear()
```

`Command` 为带类型的请求，覆盖：设定播放状态、seek、上一首/下一首、Jump、替换队列、改变模式、开始电台、自然结束。具体类型只携带相应参数；跨异步边界前复制切片。

`Playback` 包含队列、实际播放顺序、当前位置、播放意图及模式。相同队列/歌曲只调整需要的状态；不能每次快照都重新加载音源。空队列用 `Clear` 明确处理。

操作约束：

1. 没有 `Control` 或返回 false，保留当前个人播放行为。
2. 处于准备加入、在房、重连或退出阶段时，由接入层处理相关命令并返回 true；不允许同步失败时悄悄退回独立切歌。
3. `TogglePlay` 在写队列出队时按最新确认状态转换为 PLAY/PAUSE；连续点击按顺序处理，远端不接收 toggle。
4. `Apply` 只走内部执行函数，远端状态及确认后的本地操作都通过它应用，统一绕过命令接管。
5. 把现有公共方法相互调用的部分抽成私有执行方法，避免 `PlayRadio → PlayQueue`、`Next → load` 一次操作多次接管。
6. 自动事件仅在其加载代次仍有效时处理。`Changed` 和加载完成通知不承担命令上报职责，因此不需要依赖“500ms 内不发送”之类的时间窗口防回环。
7. `Apply` 校验队列、顺序、索引、进度，使用现有 `gen`/`seekGen` 丢弃旧异步结果；不能新增一套音频播放器。

### 5.3 需要覆盖的当前入口

| 当前方法/来源 | 调整 |
| --- | --- |
| `TogglePlay`、媒体键的明确 Play/Pause | 明确目标状态后统一接管；幂等的设置播放状态由内部执行完成 |
| `Next/Prev/Jump` | 接管后由会话根据最新共同队列确定目标歌曲 |
| `Seek` | 在音源未就绪时也产生一次命令；最终异步 seek 不重复发送 |
| `PlayQueue` | 把新的普通歌曲队列作为一个整体请求，不边替换边上报 |
| `ToggleShuffle/CycleRepeat` | 未验证模式协议时拒绝修改，提示首版范围；不得只改变本机模式 |
| `PlayRadio/RadioFrom/AttachRadio/EndRadio` | 接管检查必须在修改队列或 feed 之前；会话内阻止启动电台 |
| `ended()` | 发出自然结束事件；外部会话接管时不执行默认 Next/RepeatOne |
| `loadSkipping()` 失败分支 | 外部管理模式不自动跳过下一首；发布本机不可播放状态 |
| `Restore` | 仅用于应用生命周期恢复；一起听期间不通过它绕过会话控制 |

首版以 `Control != nil` 表示播放器处于外部管理模式：app 仅在 Connecting 至 Leaving 期间安装处理器，Idle 时解除，不再维护一个可能与处理器脱节的 managed 开关。处理器在这些阶段必须消费全部相关控制请求。进入时取消旧电台 feed，递增其代次；退出解除处理器后，个人播放继续使用原来的自动结束/跳过策略。

主窗口、托盘、系统菜单、Touch Bar、刘海和媒体键现有调用可保持原样，因此不用给每处按钮增加“是否一起听”分支。新增入口及“不支持该操作”的反馈由 app 层提供。

## 6. 一起听会话与线程模型

`app` 持有一个会话实例。会话状态和播放器访问均在主线程；网络调用在工作 goroutine，结果通过应用的 `post` 返回主线程。

会话对播放器只依赖窄端口：读取本机播放快照、应用目标状态、清空/停止。歌曲详情解析通过 API 接口复用 `netease`，不让房间模块访问 `*player.Player`。

概念状态如下，代码用 `Connecting/Busy/Reconnecting/Syncing/Leaving/Closed` 和房间信息表达，避免额外维护一套并行枚举：

```text
Idle → Connecting → Active → Reconnecting → Active
          │            │          │
          └────────────┴──────────┴→ Leaving → Idle
```

- `Connecting`：检查/创建或加入，再读取首个快照。已知房间的初始化失败保留房间，允许重新同步或明确结束；取消连接后迟到的创建/加入结果执行限时清理。取消恢复已有房间不自动结束该房间。
- `Active`：保活、读取快照、接收本地命令。
- `Reconnecting`：保留当前会话身份，暂停无法确认的共同控制写入，读取状态以恢复；不自动创建新房间。
- `Leaving`：先取消调度、拒绝新操作，再执行有限时间的退出清理；旧响应不能重新激活会话。
- `Idle`：无网络轮询、无房间计时器，完全使用原播放器行为。

状态结构区分“房间运行状态”和“一次操作错误”。某次切歌被拒绝不等于房间已经失效。客户端角色来自真实返回的创建者/成员信息，不能把邀请人永远当作当前房主。

每次连接创建独立会话和 context，API 绑定账号，操作捕获房间 ID。app 回调检查会话实例身份；会话内 epoch 让旧轮询响应失效。退出/切换账号取消 context，防止迟到结果重新激活会话。

调度只在房间会话内存在，隐藏窗口继续同步，真正退出才清理。复用项目的主线程 post 约定，不保存 `ui.Context` 或帧内 `ui.Element` 到任务中。

## 7. 同步算法与失败语义

### 7.1 创建与加入

1. 检查登录，读取当前账号房间状态；已在其他房间时展示真实状态，不自动覆盖。
2. 深拷贝个人 `player.Session`，记录有无队列及电台来源。连接期间冻结新的播放控制，防止备份和实际播放器分叉。
3. 创建方从当前普通歌曲队列生成初始列表；首版要求至少一首可播放歌曲。加入方先检查邀请再接受。
4. 成功后读取房间及队列/播放快照。加入方不得把个人队列上传覆盖房主队列。
5. 解析歌曲详情、应用共同队列及初始位置，启动心跳和状态读取。
6. 未建立房间的失败恢复个人快照；已知房间的半完成操作保留错误和重新同步/结束入口。结果未知时通过“恢复当前房间”查询，不盲目重复创建/加入。

### 7.2 本地命令发送

- 由 `Control` 收到明确操作，转换为一起听领域动作，再由网络适配层编码网易云协议。
- 播放命令使用会话内递增 `clientSeq`；队列变更使用独立版本，二者从当前毫秒时间起步。恢复时不重放上一会话写请求；跨设备的版本冲突语义仍待验证。
- 写请求串行，seek 只合并尚未发送且作用于同一歌曲的中间位置；不能跨切歌合并。
- 首版采用服务端确认后应用本机目标状态，UI 显示操作进行中。连续按键基于待执行意图顺序处理，避免都从同一个旧状态计算。
- 替换队列后再发送定位当前歌曲的命令。前半成功、后半失败时重新读取并对齐，不能假装这是原子事务或盲目回滚远端队列。
- 超时意味着结果未知：重新读状态确认，不无条件重发 Next、替换队列或结束房间。

### 7.3 远端命令与防回环

- 首先验证房间、账号和请求代次，再校验快照完整性与命令版本。
- 按发送者、`clientSeq/serverSeq`、类型、目标歌曲、状态及进度去重，只保存最后一个已应用指令；拒绝更旧的 serverSeq。相同指令且队列未变时不重新 Apply。
- 过滤本机已经提交的命令回显，但不能一概丢弃 `userId == 自己`：加入时服务端可能生成本人的初始对齐指令，必须通过实测样本识别。
- 远端命令通过 `Apply` 执行，加载/seek/淡出完成只发布 `Changed`，不会产生新的网络写操作。
- 发送本地命令时标记旧的在途轮询响应失效；确认后发起新读取，避免较早快照覆盖刚完成的本机操作。
- 同时操作以服务端确认后的状态为准；没有可证明的全局顺序时，不声称实现了严格冲突解决或恰好一次投递。

### 7.4 进度与加载延迟

- 保存快照采样时刻和单调时钟。只有播放状态为 PLAY 才补偿经过时间，暂停位置保持不动。
- 若服务端提供可靠采样时间，用已验证语义换算；否则请求往返中点只能作为估算。不能把很早的最后一条播放命令当成刚采样的实时位置。
- 先加载目标音源，再根据最新快照校准。等待歌曲详情和音源时继续接收新状态，旧加载结果不得覆盖新歌曲。
- 普通重复读取不 seek；新指令、队列改变、明确重新同步、重连或超过 15 秒没有读回时重新对齐。解码器就绪后，若连续两次读取发现本地播放状态不符或进度偏差超过 2 秒，也自动对齐。加载/seek 后留出 3 秒稳定时间，曲终附近等待下一条指令，避免重复播放旧曲。位置仍为基于服务器时钟的估算，并非实时采样。
- 位置限制在曲尾前；参与者自然结束后的重复快照不重播。由于协议仅提供目标歌曲 ID，同一歌曲在队列中重复出现时，GOTO 无法可靠区分实例，当前选取第一个匹配项；此项不算已解决。

### 7.5 自然结束和不可播放

双人房间内不得由两个播放器独立无条件 Next。当前采用的保守策略为：创建者负责主动报告自然推进，参与者曲终先读取最新状态；若官方端采用不同协调规则，按实测调整。不能仅凭客户端角色假定官方端会服从本项目策略。

一方无版权、无会员权限、音源加载失败时，仅该端显示失败并等待下一条有效房间状态，不擅自跳歌或给另一方换歌。各端使用自己的音源权限，不通过房间共享音频 URL 来假定权限一致。

### 7.6 心跳、读取和重连

- 心跳维持成员在线，快照读取用于接收操作，两者不能混同。
- 当前采用完成后 2 秒读取、至少每 10 秒心跳，并随心跳检查房间状态；timeSpan 的单位未确认，暂不直接用于调度。参数仍需按集成实测延迟和频控调优。
- 播放快照和写操作仍串行，每类请求最多一个在途。心跳及成员查询由独立定时器调度，每 10 秒尝试一次，整组请求共用 8 秒预算；不等待播放器 Busy，也不阻塞已取得的播放快照。退出/关闭停止保活调度，退出失败后恢复。
- 心跳中的进度来自实际播放器；未就绪/失败时不能伪报已经在正确位置播放。本地控制命令仅在音频已就绪且歌曲一致时采用本机位置，否则沿用房间时钟估算，避免加载期间冻结的 pending 位置回退另一端进度。
- 快照读取网络错误按 4/8/16/30 秒退避，暂未增加抖动；保留本地音频播放，暂停新共同控制并清空待写队列。缺失/不完整快照按 2 秒重读，不累计网络失败。非终止性心跳/成员查询失败不丢弃已读到的有效快照，也不反复重播同一条命令。当前将 301/488 作为登录/房间失效处理。读取间隔超过 15 秒视为需要重新确认与对齐。
- 首版不为低延迟提前引入 IM。若读取接口无法提供满足要求的同步状态，停止完整功能交付并另行评估接收通道，不能用提高轮询频率掩盖数据缺失。

## 8. 应用生命周期与个人会话

### 8.1 `internal/app/app.go`

- `app` 新增一个一起听接入对象字段；播放器创建后初始化，随会话状态安装/解除 `Control`。
- 保留现有 `Changed`，心跳通过快照函数读取播放器的实际就绪/失败状态，不新增状态监听通道。
- 退出前停止会话调度、取消在途任务，保护个人 session，再关闭系统播放器等资源。
- 正常退出的服务端清理应异步、有限时；不能在主线程等待依赖主线程回调的网络任务。进程立即退出时只能保证本地取消，服务端依赖心跳超时兜底，不承诺一定收到 end。

### 8.2 `internal/app/session.go`

`Player.Session()` 已改为复制 Queue/Order，个人快照不会因后续队列修改而变化。

- 一起听期间 `saveSession` 保存的是进入前个人快照，而非当前房间队列。
- 已排队的 30 秒保存回调也必须走同一选择逻辑，不能只有退出保存特殊处理。
- 加入前没有歌曲时保持“无个人会话”，退出调用 `Clear`；不误恢复旧磁盘队列。
- 正常退出房间后恢复个人队列、位置、模式且保持暂停；原电台的 feed 由 app 按现有逻辑重建。
- 不把 roomId、共同队列写入普通 session.json；应用重启后先恢复个人播放。账号仍在服务端房间时，用户显式选择恢复或结束。

### 8.3 `internal/app/ui_account.go`

`signOut` 和账号 ID 改变时，必须在凭据清除/替换前让一起听对象失效并取消请求；退出请求若发出，必须绑定旧账号凭据且不在新账号下重试。`signedIn` 同一账号资料刷新不应误结束房间。

### 8.4 邀请解析

首版接受明确的官方双人长链接：

```text
https://st.music.163.com/listen-together/share/index.html?songId=...&roomId=...&inviterId=...
```

- 使用 `net/url` 校验域名、路径、必要参数、重复冲突参数和长度；只提取数据，不执行外部深链。
- 多人 `multishare`、`isFLT=true` 跟听明确提示暂不支持，不能误送到双人 accept。
- 复制链接使用真实房间/邀请人/当前歌曲，通过 URL 编码生成。
- 短链接若纳入，需要验证官方跳转域、跳转次数及最终双人路径；未验证时提示使用完整分享链接，不直接访问任意用户输入 URL。

## 9. UI 与交互

入口沿用底部播放栏的耳机按钮，并加入当前歌曲的“更多”菜单；完整播放页顶部拖动区域不增加入口。邀请弹窗统一挂载到 `ui_main.go`，没有当前歌曲时也能加入/恢复房间。

- 未登录：使用现有登录入口。
- 未在房：邀请输入与加入按钮为主，提供发起一起听、恢复当前房间。
- 开始连接后关闭邀请弹窗；成员与阶段状态展示在完整播放页封面上方，小窗口使用双头像与状态同行的紧凑布局；封面与成员区使用相同中轴。
- 点击成员区、底部耳机或当前歌曲“更多”，使用同一房间菜单：邀请好友（二维码）、复制邀请、重新同步、离开一起听；连接中可取消。
- 后台请求 `Busy` 不影响菜单可用性；显式 `Syncing/Leaving` 才禁用相应操作。轮询过程中点击重试/离开会排队执行，避免按钮随轮询闪烁。
- 重连期间保留当前播放并自动读取；失败原因可从房间菜单查看。未建立房间就失败时重新打开邀请弹窗，保留输入。

UI 不在渲染函数中无条件发请求。列表使用稳定 key，背景任务只持有业务数据和必要服务；遵循 `.agents/skills/mygo-maintenance/SKILL.md` 的线程、元素生命周期规则。

音量保持本地。房间内请求私人 FM、播客或未支持模式时，统一提示先结束一起听，避免隐式踢出对方。即使入口仍可点击，播放器接管层也必须保证不会局部修改队列。

## 11. 验证计划

### 11.1 协议验证工具

创建/加入/结束必须由显式的 LIVE 场景选择触发，不能让普通 `go test` 或仅配置 LIVE 就自动操作账号现有房间。测试不会自动给他人发送邀请或消息。

### 11.3 官方客户端互通矩阵

1. 本项目创建，官方端加入。
2. 官方端创建，本项目加入。

每个方向测试：初始同步、双方播放/暂停、上一首/下一首、连续拖动、暂停后加入、整首自然结束、队列替换、一端不能播放、双方同时操作、隐藏到托盘、断网重连、macOS 休眠唤醒、任一端结束、账号退出。
